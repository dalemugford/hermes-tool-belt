# Codex Reasoning Cache Artifact

**Date:** 2026-05-31
**Status:** Observed; documented; not actionable from dynamic-tools.

---

## Observation

During the Mnemosyne A/B verification (which itself returned `PREFIX_STABLE`
on both profiles), Bernard's turn 3 came back with `cache_read_tokens=0`
despite identical `system_hash`, identical `tool_list_hash`, and identical
session_id to the prior two turns. Sue's turn 3 in the same time window
hit cache cleanly.

| Profile | Turn | msg_count | input_tokens | cache_read | reasoning_tokens |
|---|---|---:|---:|---:|---:|
| Bernard | 1 | 2 | 11,632 | 0 | 127 |
| Bernard | 2 | 4 | 899 | 10,752 | 67 |
| **Bernard** | **3** | **6** | **11,694** | **0** | **300** |
| Sue | 1 | 2 | 10,933 | 0 | 58 |
| Sue | 2 | 4 | 1,260 | 9,728 | 25 |
| Sue | 3 | 6 | 1,296 | **9,728** | **0** |

Both profiles: `gpt-5.4` via `openai-codex`, `api_mode: codex_responses`.

## Diagnosis

The variable that correlates with cache miss is `reasoning_tokens` on the
turn-completing-before-the-miss-turn. Bernard's turn 2 produced 67 reasoning
tokens that were then included in turn 3's prefix; Sue's turn 2 produced 25
reasoning tokens and turn 3 hit cache fine. **The signal isn't crisp on a
3-turn sample**, but the broader pattern across earlier Bernard sessions
(the 30.7% vs 61.5% hit rate split in `state.db`) is consistent with
"sometimes reasoning trace integration breaks the response chain."

Two compatible mechanisms:

1. **Response-chain TTL** shorter than prompt-cache TTL. Codex Responses uses
   `previous_response_id` to chain turns server-side. If that ID's window is
   shorter than the 5–10 min documented prompt-cache lifetime, gaps between
   turns can drop the chain even when prompt cache would still serve. Bernard's
   T2→T3 gap was 49s; Sue's was 7s — only Sue's stayed within whatever the
   actual chain TTL is.
2. **Reasoning-item byte non-determinism.** Codex emits reasoning items
   (`codex_reasoning_items` column in Hermes' messages table) that get included
   in subsequent turns' API payloads. If those items contain anything non-
   deterministic — embedded IDs, timestamps, signature blocks — every reasoning-
   producing turn breaks the prefix-hash match for downstream turns.

## What this means for the refactor

- **Not a dynamic-tools issue.** The freeze did its job: `system_hash` and
  `tool_list_hash` were rock-stable across all three turns on both profiles.
  The cache break lives downstream of where the plugin's narrowing decisions
  live.
- **The Mnemosyne A/B is still cleanly resolved as `PREFIX_STABLE`.** Mnemosyne
  is not the prefix-buster on the system block. See
  [`scripts/mnemosyne-prefix-check.py`](../scripts/mnemosyne-prefix-check.py).
- **Phase 5's savings numbers for `gpt-5.4` will be noisier than for Anthropic
  models.** Reasoning-producing turns can cold-cache the next turn regardless
  of what the plugin does. Any restated savings headline should note this
  explicitly rather than averaging over it.
- **The schema-token savings the freeze delivers are unaffected.** Tools are
  stable; the issue lives in conversation history bytes.

## What to do (none of it urgent)

- Add `reasoning_tokens_prior_turn` as a join column in the analyzer's
  cohort comparison, so the cohort effect can be netted out from cache
  numbers when reporting gpt-5.4 savings.
- If the cache miss pattern shows up consistently, file an issue upstream
  (OpenAI / Hermes) — but only after confirming it's not Hermes-side
  reasoning-item serialization that's the problem.
- Watch Sue once she's on Anthropic Sonnet. Anthropic's cache behavior is
  more deterministic; if Sonnet sessions don't show this anomaly, the
  story is "Codex API quirk, not architectural."
