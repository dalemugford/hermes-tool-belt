# Cache-Aware Pivot

**Date:** 2026-05-28
**Status:** Pivot decision captured; refactor not yet started. This document
is the groundwork — read before opening implementation PRs against the new
architecture.

---

## TL;DR

Provider-side prompt caching changes the economics of mid-session tool
mutation. Tool schemas sit in the cached prefix; changing them per turn
invalidates the entire conversation history after the tool block, which is
billed at the full input rate. On any reasonably long session, the cache
miss cost on accumulated history dwarfs the schema-token savings from
narrowing.

**Decision:** dynamic-tools pivots from a per-turn predictor model to a
**cache-aware mode-switching model**. The core architectural rule:

> **Only reshape tools at moments that already cost a cache break:
> session start, session end, and compaction events.**

The per-turn predictor doesn't die — it relocates to between-session
boundaries where mutation is free.

---

## What we discovered

### The mechanism

`__init__.py` patches `AIAgent._build_api_kwargs` to filter `kwargs["tools"]`
to `(always_on ∪ triggered ∪ expanded) ∩ ceiling` on every API call. The
tool list in the outbound payload changes per message based on predictor
output.

Provider-side prefix caching (Anthropic, DeepSeek) operates on the whole
message array prefix:

```
[system_message, ...tool_schemas..., conversation_history]
```

Tool schemas come **right after** the system message and **before**
conversation history. If we send 15 tools on turn 1 and 20 tools on turn 2,
the prefix diverges at the tool-schema boundary — and **the entire
conversation history prefix goes cold**.

### The unmeasured cost

The current savings model measures only `Δschema_tokens` (a small, bounded
quantity). It does not subtract the cost of `cache_read_tokens` lost when
the prefix breaks. That cost is:

```
cache_miss_cost = history_tokens × (miss_price − hit_price)
```

`history_tokens` grows monotonically through the session. `miss_price /
hit_price` is roughly 10× on most providers (Anthropic Sonnet ~3.75/0.30
per MTok; DeepSeek V4 ~0.14/0.0028). The crossover point — where
narrowing-driven cache breaks start costing more than they save — comes
fast on any session that runs more than a handful of turns.

### Three concrete failure modes

1. **Inter-turn churn**: narrow on turn N, expand on turn N+1 → history
   prefix cold.
2. **Intra-turn churn**: `expand_tools` mutates state mid-reasoning-loop →
   cache breaks **within a single user turn**, on the most expensive turns
   (tool-heavy ones).
3. **Unmeasured cost**: the ledger has no `cache_read_tokens_lost` column.
   The plugin currently reports savings that don't account for any of this.

### Why we may not have noticed

If providers in use don't honour cache breakpoints (or Hermes doesn't set
them), there's no caching to break — and the original predictor model is
fine. This is the load-bearing empirical question and is addressed below.

## The unifying principle

> **Only mutate tools at moments that already cost a cache break.**

There are three such moments in a session's lifetime:

| Moment           | Cache state           | Mutation cost |
|------------------|-----------------------|---------------|
| Session start    | No prefix yet         | Free          |
| Compaction       | Already invalidated   | Free          |
| Session end      | Session is over       | Free          |

Any mutation **outside** these moments pays the full
`history_tokens × miss_premium` penalty. The redesign collapses to this rule.

---

## The new architecture

### Mode detection

Caching may or may not be wire-active depending on provider, model, and
upstream Hermes configuration. We treat this as a runtime property to
detect, not an environment property to assume.

**Config:**

```yaml
cache_mode: auto  # auto | on | off
```

- `auto` (default): observe `cache_read_tokens` for the first few turns of
  each session and self-select. Log a warning if reality diverges from the
  selected mode mid-session.
- `on`: assume caching is active. No in-session tool mutation.
- `off`: assume caching is inactive. Per-turn predictor and narrowing as
  today.

**Safe default = assume caching is on.** Asymmetric cost: wrong-assuming-off
in a cache-on environment burns money every turn; wrong-assuming-on in a
cache-off environment leaves some narrowing on the table but doesn't
actively lose. Bias the default toward the cheap failure mode.

### Cache-on mode (the new default)

- **Session-start tool selection.** The analyzer picks the tool set once at
  session start based on profile + context. Stable prefix for the session's
  lifetime.
- **No in-session mutation.** The per-turn predictor does not fire. The
  `_build_api_kwargs` filter still runs, but with a frozen set computed at
  session start.
- **`expand_tools` remains** as the runtime escape valve. When the model
  reaches for an absent tool, we pay one cache break, but that's the model
  asking — not the plugin guessing.
- **`apply.py` runs at:**
  - Session end (always)
  - Compaction events (free reshape — cache is already broken)
- **The predictor relocates between sessions.** Instead of mutating tools
  per turn, the predictor consumes the prior session's telemetry to shape
  the *next* session's starting ceiling. Same model, same signal, same
  intelligence — applied at the only moment where mutation is free.
- **Learning signal:** every time `expand_tools` fires, it's evidence that
  the default set was too narrow for this profile. Aggregated across
  sessions, the next session's default ceiling grows.
- **Cold start:** new installs use the historical-replay feature to
  bootstrap a starting ceiling from the user's existing
  `~/.hermes/sessions/*.jsonl`. No "first hundred sessions are conservative"
  penalty.

### Cache-off mode (preserves original behaviour)

- In-session narrowing/expansion via per-turn predictor (original
  behaviour).
- `apply.py` at session end / compaction.
- Predictor enabled to further shape during the session.

### What's scrapped

- **Early-window prediction with mid-session lock** was considered (predict
  at turn 3, lock for the rest of the session). Scrapped: the
  between-session predictor relocation makes it redundant. `apply.py`
  itself runs at session end and shifts tools in/out for the *next*
  session — which is the same intelligence, applied at a strictly cheaper
  moment.

## What survives, dies, relocates

| Component                                  | Cache-on mode             | Cache-off mode |
|--------------------------------------------|---------------------------|----------------|
| `_build_api_kwargs` patch                  | Stays (frozen set)        | Stays          |
| Per-turn `predictor.py`                    | **Dies in-session**       | Stays          |
| Predictor as between-session shaper        | **New role**              | N/A            |
| `expand_tools.py` (safety valve)           | Stays                     | Stays          |
| `apply.py` at session end                  | Stays                     | Stays          |
| `apply.py` on compaction                   | **New trigger**           | New trigger    |
| `learned.py` adaptive overlay              | Stays (between sessions)  | Stays          |
| Sticky residency / lookback                | **Dies** (was per-turn)   | Stays          |
| `analyze.py`                               | Stays                     | Stays          |
| Historical-replay bootstrap                | Stays                     | Stays          |
| Telemetry (`predictions.jsonl` etc.)       | Stays                     | Stays          |
| **New: `cache_read_tokens_lost` column**   | **Required**              | Required       |
| **New: `cache_mode` detection logic**      | **Required**              | Required       |

## Verification before refactor

The pivot is **conditional on caching being wire-active** in real
environments. Before code lands, confirm:

1. **Does Hermes set `cache_control` breakpoints on outbound requests?**
   Anthropic caching is opt-in per request via explicit markers. No
   markers → no caching → the pivot is moot and current predictor model
   is fine.
2. **Where is the cache breakpoint placed?** If after `system` but before
   `tools`, tool mutations don't invalidate the system cache. If at
   end-of-tools (typical), every tool array change invalidates everything
   after.
3. **Empirical check in `state.db`:**
   ```sql
   SELECT session_id, input_tokens, cache_read_tokens, cache_write_tokens,
          api_call_count,
          round(cast(cache_read_tokens as float)/nullif(input_tokens,0)*100, 1)
            AS cache_pct
   FROM sessions ORDER BY created_at DESC LIMIT 20;
   ```
   Cross-reference with the `tool_set_changed` field (already landed in
   `predictions.jsonl`) to see whether mutation-heavy sessions exhibit
   collapsed `cache_pct` relative to stable sessions.

The recently-landed `tool_set_changed` field is the evidence axis. First-turn
hits are always `true` (cold start) — exclude them. Mid-session mutations
(`turn > 1 AND tool_set_changed = true`) are the cost driver to measure.

If empirical `cache_pct` stays high even in expand-heavy sessions,
providers are doing tolerant partial-prefix matching and the concern is
theoretical. If it collapses, the pivot is justified and urgent.

## Implications for current code

These are observations, not a task list — the refactor will define the
actual order of operations.

- **`predictor.py`**: the per-turn prediction logic needs to be addressable
  as a between-session shaper. Likely a separate entry point that consumes
  `predictions.jsonl` + `tool_calls.jsonl` and emits a starting ceiling for
  the next session of the same profile.
- **`__init__.py`**: the `_build_api_kwargs` patch needs to read frozen-set
  state in cache-on mode, mode-detection logic, and a hook for compaction
  events.
- **`apply.py`**: needs a compaction-triggered path in addition to its
  session-end path.
- **`logger_io.py` / telemetry**: a new `cache_read_tokens` field per turn
  is required to validate the pivot empirically (and to feed the
  `cache_read_tokens_lost` column in the savings ledger).
- **`policy.yaml`**: the `cache_mode` knob needs a schema entry.
- **`STRATEGY.md` / `PLAN.md`**: both will need updates once the refactor
  lands. They currently describe the per-turn predictor as the active
  narrowing path — the cache-on default contradicts that.

## Open questions

- **Mode-switching mid-session.** If `auto` mode detects caching is on for
  the first three turns and then provider-side caching collapses (provider
  outage, cache pool eviction), do we switch to cache-off mode mid-session?
  Probably not — switching itself would invalidate the cache. Better: log
  the divergence and keep the assumed mode for the session's life.
- **Profile granularity for between-session shaping.** What's the
  identifier we shape against? Profile name alone? Profile + working
  directory? Profile + initial system prompt hash? Need to pick a key
  that's stable enough to accumulate signal but specific enough to
  differentiate distinct workloads.
- **Compaction hook surface.** Does Hermes emit a compaction event we can
  subscribe to? If not, what's the cleanest way to detect it from the
  plugin side?
- **Savings model rewrite.** The current ledger reports
  `tokens_saved_via_narrowing`. The new ledger needs to net out
  `cache_read_tokens_lost`. Reporting numbers continue to be reported
  without this correction is misleading.
