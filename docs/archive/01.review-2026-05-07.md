# dynamic-tools Review — 2026-05-07

Reviewed `~/.hermes/plugins/dynamic-tools`.

## Summary

The core mechanism is sound. The plugin is already shaped like something that can move into Hermes core, but the telemetry and config model need a pass before it learns from usage.

## What’s there

- `__init__.py`: registers plugin, patches `AIAgent._build_api_kwargs`, runs gateway pre-dispatch prediction, filters per API request, logs prediction rows, registers `expand_tools`.
- `predictor.py`: simple regex/attachment classifier.
- `presets.py`: loads `aggressive`, `balanced`, `conservative`; applies global/channel overrides.
- `expand_tools.py`: mutates the current prediction ContextVar expansion set, then next API call widens tools.
- `logger_io.py`: append JSONL telemetry for predictions/tool calls.
- Presets: three static YAML profiles.

Compile check passed with:

```bash
python3 -m compileall -q /Users/macmini/.hermes/plugins/dynamic-tools
```

## Good parts

- Patching `_build_api_kwargs` is the right place. Cached agents don’t break it.
- `agent.tools` remains canonical. Good separation.
- `expand_tools` works as a safety valve through the mutable ContextVar.
- Unknown tools pass through instead of disappearing. Sensible plugin-era default.
- Failure mode falls through to no-narrowing.
- Current savings are real: local telemetry showed ~60 real prediction rows, average saved ~7,719 estimated tokens, ~62.5% reduction.

## Issues to fix before core

### Channel logging is currently broken

All real prediction rows had `channel: ""`. That blocks the “per-channel learning” idea until fixed. `_channel_from_event()` doesn’t seem to be finding the Telegram platform from the hook event/kwargs. Gateway logs have `platform=telegram`, but plugin rows don’t.

### README is stale in the architecture section

It still says the plugin patches `model_tools.get_tool_definitions`, consumes/clears the ContextVar, and mutates `self.tools` via an agent registry. The code no longer does that. Anyone maintaining this later will be led into the weeds.

### Manifest advertises a hook that is not registered

`plugin.yaml` lists `on_session_start`, but no hook is registered. Harmless, but sloppy.

### Per-channel overrides only work by exact channel key

Given current blank channels, unusable. Once fixed, source identifiers need normalization: `telegram`, `telegram:dm`, `telegram:chat:<id>`, `slack:#channel`, etc.

### Channel override docs imply custom triggers, but implementation ignores them

`presets.py` docstring says channel config may set `triggers`; `_resolve_preset_inner()` never applies them.

### Tool-call logging is too thin for learning

It logs `expand_tools` args/results only now, which is useful, but most historical rows lack args/results. Adaptive management needs every row to capture enough context to reconstruct miss/waste patterns.

### Prediction rows don’t log the actual allowed tools

Counts are useful for savings, but adaptive tuning needs names: base tools, trigger-added tools, unknown-kept tools, expanded tools.

### False positives are hard to measure

You can infer trigger fired and no matching tool call, but there’s no direct mapping logged from trigger → admitted tools → actual calls.

### False negatives are only visible through `expand_tools`

That’s acceptable as a start, but the log should store requested category, resolved tools, and subsequent first real tool call.

### Shell trigger is broad

The message “I think it’ll make its way into core when I release it...” fired `shell`, likely from `release`. That admitted `terminal` for a product-strategy message. Cost only, no behavior bug.

### File-write trigger is broad

Words like “change”, “fix”, “update”, “delete” are common in conceptual conversation. Might be okay in aggressive because write tools are cheap-ish compared with terminal/browser, but it will create noisy false positives.

### Unknown-tool safe default is right for plugin safety, but questionable for core

In core, unknown should probably be classified into `uncategorized_always_on` only during dev/debug, with warnings or a generated categorization report.

### No policy versioning

Prediction rows log `preset`, but not plugin version, preset hash/version, trigger version, or config hash. Future analysis will mix policies unless this gets added.

### No adaptive state layer exists yet

Expected, but the current preset shape needs somewhere to write learned always-on sets.

## Telemetry observation

Current telemetry suggests `expand_tools` calls are mostly asking for `terminal`. Aggressive is sharp, but terminal may become channel-learned for Dale’s Telegram DM because “review/debug/check” often becomes shell work even when the message doesn’t look shell-y.

## Core-worthy shape

Replace preset names with one base policy:

- `base_always_on`
- `protected_always_on`
- `trigger_groups`
- `learned_always_on_by_channel`
- `always_off`

Keep static YAML as the seed format.

Add a learned state file, probably under Hermes state:

```text
~/.hermes/state/dynamic-tools/channel_policy.json
```

Expand prediction logs to include:

- `channel`
- `policy_version`
- `config_hash`
- `base_tools`
- `learned_tools`
- `trigger_tools`
- `unknown_kept_tools`
- `cut_tools`

Expand tool-call logs to include:

- `toolset`
- `was_initially_available`
- `required_expand_tools`
- `expand_category`
- `turn_index_after_expansion`

## First concrete fixes

1. Fix channel extraction and decide normalized channel granularity.
2. Update README to match the `_build_api_kwargs` architecture.
3. Remove `on_session_start` from manifest or register a real hook.
4. Add preset/config hash to `PredictionRecord`.
5. Log actual tool-name sets, not just counts.
6. Add an analyzer script that joins predictions/tool calls and reports:
   - expand burn rate per tool/category
   - false-positive trigger rate
   - always-on unused rate
   - promotion/demotion recommendations per channel
7. Narrow the shell trigger so “release” doesn’t imply terminal.
8. Implement learned always-on as recommendation-only before auto-apply.

## Bottom line

The quiet bug is the blank channel. The architectural gap is telemetry detail. The preset itself is good enough to leave mostly alone while the data layer gets smarter.
