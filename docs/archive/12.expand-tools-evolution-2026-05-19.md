# Evolving `expand_tools`

> **2026-05-31 NOTE — urgency dropped post-pivot.** Under cache-on
> (the default), the frozen session ceiling is sane out of the gate and
> `expand_tools` is a safety valve rather than the primary narrowing
> mechanism. The granularity improvements below stay nice-to-have but
> aren't blocking. The "tools that get reached for repeatedly join the
> frozen ceiling" loop is now handled by
> [`scripts/shape-ceiling.py`](../scripts/shape-ceiling.py) at session
> boundaries (Phase 2 of doc 16) — making per-tool expansion mostly
> a polish item.

Ideas for improving the plugin's escape hatch without losing the properties
that make it useful today: cheap, inspectable, safe, and easy to recover from
when the predictor guessed wrong.

This document exists because the current `expand_tools(category="...")`
mechanism works, but it expands in coarse units. That is fine while categories
stay small. It gets expensive and blunt once a category contains many tools.
The next round of work should make expansion more precise before introducing a
heavier retrieval stack.

---

## Current behavior

Today the plugin exposes one recovery primitive:

- `expand_tools(category="browser")`

The handler resolves the toolset name to concrete tools, appends that category
and its tools to the prediction state's `expansions` set, and the patched
`_build_api_kwargs` unions those tools into the next API call. Sticky residency
then keeps the expanded tools available for a few more turns.

That gives the model a practical way to recover from over-aggressive narrowing.
It is already a good design. The main weakness is granularity.

---

## Design principle

**Make recovery more precise before making it more intelligent.**

There is a live temptation to jump straight to embedding retrieval, graph
search, or ToolRAG-style infrastructure. That may prove useful later. The
simpler win is to turn `expand_tools` from a category-sized hammer into a more
surgical instrument.

The ordering in this doc reflects that bias.

---

## Candidate improvements

### 1. Tool-level expansion

**Shape:**

```json
{"tool": "read_file"}
```

or

```json
{"tools": ["read_file", "search_files"]}
```

**Why this is attractive:**

- Lowest-cost improvement with the clearest payoff.
- Preserves the current mental model: the model asks for what it needs, then
  gets it on the next call.
- Avoids loading an entire category when only one tool was missing.
- Fits naturally with existing telemetry and `resolved_tools` reporting.

**Useful telemetry to add:**

- `requested_tools`
- `resolved_tools`
- `unused_expanded_tools`
- `expansion_granularity: "tool" | "category" | "bundle"`

**Main risk:**

- The model may request one tool when the real workflow needs two or three.
  That is manageable; it just argues for the bundle work below.

**Recommendation:** first implementation target.

---

### 2. Tiered category expansion

**Shape:**

```json
{"category": "file", "tier": "minimal"}
```

Possible tiers:

- `minimal` — smallest useful read-only subset
- `write` — write/edit subset
- `full` — today's current behavior

**Example for `file`:**

- `minimal` → `read_file`, `search_files`
- `write` → `read_file`, `search_files`, `write_file`, `patch`
- `full` → full toolset resolution for `file`

**Why this matters:**

- Gives the plugin a middle ground between one-tool and whole-category.
- Matches how many toolsets are actually used: there is often a read path, a
  write path, and a rare advanced path.
- Keeps the schema simple and explainable.

**Telemetry worth adding:**

- tier requested
- tools loaded by tier
- unused-tool count per tier
- tier escalation rate (`minimal` → `write` → `full`)

**Main risk:**

- Tier definitions become policy surface that has to be maintained.
- Some categories may not justify tiers at all.

**Recommendation:** second implementation target, starting with `file`,
`terminal`, and `browser` only if the category naturally decomposes.

---

### 3. Learned micro-bundles

**Shape:**

The plugin learns that certain tools tend to travel together and exposes them
as small expansion bundles.

Examples:

- `read_file` + `search_files`
- `write_file` + `patch`
- `terminal` + `process`

**Why this is attractive:**

- Uses the plugin's real advantage: production telemetry.
- Gives better recovery than tool-level-only expansion when workflows are
  predictably paired.
- Avoids the cost of whole-category expansion without forcing the model to ask
  multiple times.

**Possible implementation path:**

- Mine `tool_calls.jsonl` for frequent post-expansion co-usage.
- Emit bundle candidates in the analyzer.
- Start with recommendations only; make auto-apply a later step.

**Useful metrics:**

- bundle hit rate
- bundle over-expansion rate
- net saved round-trips vs. single-tool expansion

**Main risk:**

- Learned bundles can drift if user behavior changes.
- They need clear auditability so the plugin does not feel magical.

**Recommendation:** third target, after tool-level and tiered expansion exist.

---

### 4. Query-driven expansion / tool search

**Shape:**

```json
{"query": "read a local file and patch it"}
```

The plugin would return a small ranked set of tools or a tool reference set,
then expand those on the next call.

**Why this is interesting:**

- It moves toward the Anthropic Tool Search pattern while staying
  Hermes-native.
- It scales better once the tool universe gets large or plugin-heavy.
- It creates a future bridge to MCP-heavy profiles where category names are too
  crude.

**Why this should wait:**

- It is a second system.
- Retrieval quality becomes the new failure mode.
- It is much harder to explain and test than deterministic expansion.

**Recommendation:** long-horizon path, only after simpler granularity fixes
show real limits.

---

### 5. Auto-follow expansion

**Shape:**

If the plugin can see that the model is clearly reaching for a missing
capability, it expands automatically without spending a tool call on
`expand_tools` itself.

Examples:

- assistant text explicitly says it needs browser access
- model produces a near-miss tool plan that maps cleanly to a missing category
- a missing-tool error pattern can be deterministically recognized

**Why this is attractive:**

- Best user experience when it works.
- Cuts a round-trip in the exact cases where narrowing guessed wrong.

**Why this is dangerous:**

- Crosses from explicit recovery into inferred behavior.
- Easy to make spooky.
- Easier to hide mistakes, which weakens operator trust.

**Guardrails if explored:**

- off by default
- only for high-confidence deterministic cases
- explicit telemetry field marking every auto-follow event
- hard per-session budget

**Recommendation:** experimental only.

---

### 6. Expansion budgeting and bundle-efficiency metrics

This is less a new feature than a missing measurement layer.

Today the plugin knows when expansion led to real use. The next question is
whether the expansion was **too broad**.

**Useful new metrics:**

- unused expanded tools per event
- percent of expanded tools actually used
- average tools loaded per successful recovery
- average extra token cost per recovery path
- category over-expansion ranking
- sticky-assisted delayed-use rate

**Why it matters:**

Without this, category expansion can look successful while still being wasteful.
This measurement is what turns the evolution work above from taste into data.

**Recommendation:** build alongside the first granularity upgrade.

---

## Suggested implementation order

### Phase 1 — make expansion smaller

1. Add **tool-level expansion**.
2. Add **over-expansion telemetry**.
3. Keep category expansion as the compatibility fallback.

### Phase 2 — add structured middle ground

1. Add **tiered expansion** for the categories that clearly justify it.
2. Measure tier escalation and unused-tool rates.

### Phase 3 — let telemetry shape the recovery path

1. Analyzer surfaces **bundle candidates**.
2. Human review first.
3. Consider learned bundle application only after the signal is stable.

### Phase 4 — decide whether search is actually needed

1. Revisit **query-driven expansion** only if category/tier/bundle recovery is
   still too blunt.
2. If introduced, keep it optional and heavily instrumented.

---

## What not to do yet

### Do not jump straight to embeddings or ToolRAG infrastructure

That path may become valuable later, especially for MCP-heavy profiles. It is
not the next step. The plugin's current advantage is that it is easy to reason
about, cheap to run, and operationally legible. The next improvements should
preserve that character.

### Do not make auto-follow the default recovery path

Explicit recovery is part of why the current system feels safe. If the plugin
starts silently widening tool availability, trust gets harder to maintain.

---

## Short version

The best near-term move is not "smarter prediction." It is **more precise
recovery**.

If `expand_tools` evolves from category-sized expansion to tool-level, tiered,
and eventually telemetry-shaped bundle expansion, the plugin keeps its current
simplicity while recovering more cheaply and more often.
