**Date:** 2026-05-30

## Empirical baseline (Bernard, gpt-5.4 / openai-codex, 219 calls / 54 turns)

The verification run produced numbers that make the pivot non-optional:

| Call type (call-over-call hash compare, within session) | n | Hit rate | Avg cached | Avg fresh |
|---|---:|---:|---:|---:|
| **Hash mutated** | 58 | **22.6%** | 5,826 | **19,944** |
| **Hash stable** | 160 | **90.6%** | 31,130 | 3,216 |

- Inter-turn mutation rate: **49.1%** of comparable turns
- Intra-turn mutation: **21 of 39** multi-call turns had >1 distinct `tool_list_hash` (54%)
- Cache hit rate climbs from 30.5% on call 1 of a turn to ~98% by call 13 *when nothing mutates in between* — every mutation resets that climb

Per-mutated-call cost: ~17K extra fresh tokens billed at full input rate vs the stable counterfactual. Schema-token savings cannot net positive against that.

Sue's batch would add an Anthropic comparison. Not run; not required for the decision.

### Load-bearing assumption that needs verification before Phase 1 ships

The empirical numbers treat `tool_list_hash` stability as a proxy for cache-prefix stability. That holds only if **nothing else mutates the cached prefix between turns**. Mnemosyne is the obvious threat: it fires `pre_llm_call` and injects memory content into the message array, which can change prefix bytes *before* the tools block. The fact that stable-hash calls hit 90.6% (not catastrophically lower) suggests Mnemosyne's injection lands in a cache-friendly position — likely on the most-recent message, which sits inside the last breakpoint and doesn't invalidate earlier breakpoints. But "suggests" isn't "verified."

**Pre-Phase-1 gate:** run a controlled A/B with `cache_mode: on` and tool-set frozen, comparing api_calls.jsonl rows under Mnemosyne-on vs Mnemosyne-off. If the Mnemosyne-on hit rate collapses, the freeze headline is partly Mnemosyne's, not ours, and the savings story changes shape. If the gap is small, the original story holds and we proceed.

## Design principle (load-bearing — don't lose this)

**Usage-aware tool loading: carry what's needed, drop what isn't. Per-tool granularity, learned from real usage signal.**

This principle is unchanged across cache-on and cache-off modes. What changes under cache-on is the *cadence* of adjustment — not the goal, not the granularity. Adjustments happen at moments that already cost a cache break (session start, compaction, session end) instead of every turn.

Corollaries:

- **`expand_tools` is the learning signal, not a fallback.** Every model-driven expansion is direct evidence that a tool was needed and wasn't in the frozen set. Next session's shaper folds the specific tools that got reached for (per tool, not by bundle) into the ceiling.
- **Pruning is symmetric.** Tools in the frozen set that go unused for N sessions get demoted. Same evidence axis (tool_calls.jsonl), opposite direction.
- **The unit of decision is the tool, not the toolset.** "Mnemosyne is a special bundle, include all 17" would be the lazy fix. The right behavior is: if `mnemosyne_recall` gets reached for repeatedly, it joins the frozen set; `mnemosyne_triple_search` doesn't, if it never gets called. The fact that they share a toolset is incidental.
- **Don't try to be clever per turn.** Triggers, regex, lookback, sticky residency — all of these are attempts to predict per-turn intent. Cache-on mode says: don't bother, the cost of being wrong dwarfs the benefit of being right. Make the call once per session boundary using real data, then commit.

The pivot isn't a retreat from intelligence; it's a relocation of the same intelligence to a cheaper moment, fed by stronger signal (actual expand_tools events) than weaker (regex trigger guesses).

## Architecture target

The runtime mode-detect + freeze-per-session model from doc 15, with one structural tweak from what we learned about Hermes hooks:

- Available hooks (verified): `on_session_start`, `on_session_end`, `on_session_finalize`, `on_session_reset`, `pre_gateway_dispatch`, `post_tool_call`, `post_api_request`.
- **There is no `post_compaction` hook today.** That's the only piece of the doc-15 plan that needs core-side work; everything else is in-plugin.

```yaml
# policy.yaml
cache_mode: auto         # auto | on | off
cache_auto:
  detect_turns: 3        # turns to observe before locking the mode
  on_threshold: 0.40     # hit_rate ≥ this → conclude cache is on
```

State surfaces:
- `_FROZEN_BY_SESSION[session_key]` — the locked tool-set decision for the session's lifetime in cache-on mode. Cleared on `on_session_end` and on `on_session_reset`.
- `_CACHE_MODE_BY_SESSION[session_key]` — `"on" | "off" | "pending"`. `pending` during the first `detect_turns`; flips once based on observed hit rate.
- Both keyed by canonical `session_key` (the gateway shape used elsewhere), not the AIAgent uuid.

## Phases

### Phase 0 — plumbing (no behavior change)

1. Add `cache_mode` and `cache_auto` to `policy.yaml` schema; load via `_load_user_config`.
2. Add `_FROZEN_BY_SESSION` and `_CACHE_MODE_BY_SESSION` dicts at module level. Eviction in `_on_session_end` and the new `_on_session_reset`. **`on_session_reset` keeps the same `session_key` but clears history — the eviction must guarantee the *next* `pre_gateway_dispatch` re-freezes, not reuses a stale entry. Write the test for this in Phase 0, not later.**
3. Register `on_session_reset` hook → eviction only, no decision logic yet. `/reset` busts the cache identically to a fresh session, so the frozen set has to be discarded.
4. Wire `post_api_request` to also update `_CACHE_MODE_BY_SESSION` while it's `pending` (running hit-rate over the first N calls). No effect on narrowing yet.
5. **Build the replay test harness now.** A small script that reads `api_calls.jsonl` + `predictions.jsonl`, simulates the freeze decision against that history, and reports the projected mutation rate and projected hit rate under the proposed logic. Every subsequent phase exit-checks against it.

Exit criteria: telemetry shows `cache_mode_detected` field on rows; behavior unchanged; replay harness runs against current data and reports baseline.

### Phase 1 — cache-on freeze (the meat)

1. In `_on_pre_gateway_dispatch`:
   - Resolve `session_key`.
   - If `cache_mode` resolves to `"on"` for this session and `_FROZEN_BY_SESSION[session_key]` exists: use the frozen `allowed_tool_names`, skip predictor invocation.
   - Else: run predictor as today, then store the result in `_FROZEN_BY_SESSION[session_key]`.
2. In `_wrap_build_api_kwargs`:
   - No change to the filter — it already reads from `_PREDICTION_CV`.
   - The contextvar's `allowed_tool_names` now sources from the frozen set when frozen.
3. `expand_tools` continues to mutate state mid-session. The model-driven cache break is acceptable; the plugin-driven one is not.
4. Sticky residency: **disable in cache-on mode**. Its whole purpose was to amortize per-turn re-narrowing — irrelevant once the tool set is frozen.
5. Lookback: **disable in cache-on mode**. Same reason — predictor isn't running per turn.

Exit criteria: in `cache_mode: on` on Bernard, `tool_list_hash` is identical across consecutive turns within a session except when `expand_tools` ran in between. Measured against api_calls.jsonl: mutation rate on non-expand calls should drop from 49% → near 0%.

**Open before Phase 1 ships:**
- **Sessions that never see `pre_gateway_dispatch`** (cron, subagent delegation, ACP, direct CLI) will never populate `_FROZEN_BY_SESSION` and will fall through to no-narrowing. State explicitly in code + docs: cache-on mode applies only to gateway-dispatched sessions; everything else operates as if `cache_mode: off`.
- **Subagent inheritance.** A delegated subagent fires through `_build_api_kwargs` but may share or fork the parent's `session_key`. Decide: (a) subagents share the parent's freeze, or (b) subagents always run unnarrowed. Default to (b) — narrower scope, fewer surprises, can be revisited.

### Phase 2 — between-session shaper (the intelligence relocation)

The per-turn predictor's signal is real and useful. It just lives at the wrong moment, and it's working from weaker evidence (regex triggers guessing intent) than what's now available (actual expand_tools events showing what the model actually needed).

1. New entry point `predictor.shape_next_session(scope) -> overlay`.
2. Reads from `tool_calls.jsonl` for that scope, **per-tool, not per-toolset**:
   - Tools that were reached for via expand_tools in recent sessions → promotion candidates for next session's frozen ceiling. Threshold by reach-rate and success-rate to avoid one-off noise.
   - Tools currently in the frozen set that went unused for N sessions → demotion candidates. Symmetric to promotion, same evidence axis.
3. Writes overlay to `learned.json` under a new `cache_aware_overlay` key (gated by `learned_mode` like the existing overlay).
4. Phase 1's freeze step reads this overlay as the starting ceiling.
5. Runs at `on_session_end` (free reshape — session is over).

The shaper's job is mechanically simple: read evidence, write a ceiling. The whole "be smart about intent" problem the per-turn predictor was trying to solve goes away because the evidence (expand_tools events) is direct, not inferred.

Exit criteria: tools that were reached for via expand_tools last session appear in next session's initial frozen set; tools unused for N sessions get demoted. Verified by: expand_tools call rate drops session-over-session within a stable workflow. Counter-check: unused-tool count in the frozen set decreases.

### Phase 3 — auto mode detection

1. During first `cache_auto.detect_turns` (default **5**, not 3 — 3 turns is too narrow given the call-1 cache-cold artifact in the data) of a session, `_CACHE_MODE_BY_SESSION[sid] = "pending"`.
2. In `_on_post_api_request`, accumulate `cache_read_tokens / (cache_read_tokens + cache_write_tokens + input_tokens)` over those calls.
3. **Don't lock until `total_input_tokens_observed ≥ 5,000` regardless of turn count.** A 3-turn "hi / what time is it / ok thanks" opener produces tiny inputs and a collapsed denominator — the resulting hit-rate is noise, not signal. Wait until there's enough volume for the ratio to mean something.
4. **Provider blocklist:** any session on a model in `cache_auto.providers_off` (default: `["kimi-k2.6:cloud", "gpt-5.4-mini"]` based on our state.db hit-rate evidence) skips detection and locks `"off"` immediately. Three turns of wasted observation per session adds up.
5. After both gates pass:
   - hit_rate ≥ `on_threshold` (default **0.40**, candidate for tightening to fresh-tokens-billed-per-call instead — the actual economic quantity) → `"on"` (freeze whatever set is in `_FROZEN_BY_SESSION`)
   - else → `"off"` (legacy per-turn predictor, sticky, lookback all re-enable)
6. Once locked, never switch mid-session. **Divergence handling has teeth, not just a log line:** if a session locked `"on"` shows ≥3 consecutive mutated calls with hit_rate < 0.30, emit a structured warning that the analyzer surfaces as a "freeze quality" issue. Don't auto-unlock — the cost of switching is itself a cache break — but make the failure visible for forensic review.

Exit criteria: a session on kimi-k2.6 (which our state.db query showed at 2.5% hit rate) locks `"off"` immediately via blocklist. A claude-sonnet-4-6 session auto-locks `"on"` within 5 turns *or* 5K observed input tokens, whichever comes first.

### Phase 4 — compaction handling (needs core work)

No `post_compaction` hook exists. Two paths:

**A. Patch the context compressor** (in-plugin, no core PR):
- Compaction has **three call sites**, not one — `run_agent.py:2371`, `:2396` (both `context_compressor.on_session_end(...)`), and the in-session `_compress_context` forwarder around line 4331. A monkey-patch on just one will leave ghost cache breaks that never trigger re-freeze.
- Cleanest wrap point: the `AIAgent._compress_context` forwarder on the class — single attribute, single patch, covers all flows that go through the forwarder. Verify before coding that the two `on_session_end` paths also flow through it; if not, patch the underlying compressor at `agent.conversation_compression.compress_context` instead.
- On compaction, evict `_FROZEN_BY_SESSION[sid]` and re-freeze on the next dispatch — the cache is already broken by compaction, so it's a free moment to reshape.

**B. Land a `post_compaction` / `post_compression` hook in Hermes core** and use it:
- Cleaner, reusable for other plugins, no monkey-patch fragility.
- Slower (PR review cycle).

Plan: do (A) **and** file the core PR for (B) the same day — the monkey-patch precedent isn't sacred, it's debt we're choosing to take temporarily.

**Cache TTL gets promoted into this phase.** Anthropic's `cache_control` default 5m TTL means quiet sessions can hit a "stable hash, expired cache" state where our freeze logic claims a win it didn't earn. Detect by: stable-hash call with `cache_read_tokens == 0` after >5 minutes since the previous call. Surface in analyzer; don't try to mitigate (we can't extend TTL from the plugin).

Exit criteria: post-compaction sessions show a single `tool_list_hash` change at the compaction event and stable hashes after; cache-TTL-expired calls are flagged distinctly in the analyzer.

### Phase 5 — savings ledger correction

The current analyzer reports `tokens_saved_via_narrowing` without netting out the cache-miss penalty. Numbers in marketing copy (docs 13, 14) are not defensible under cache-on conditions.

1. In `analyze.py`, compute per-mutated-call `cache_read_tokens_lost` against a **matched** counterfactual, not a global cohort average:
   - Bucket stable-call observations by `api_call_idx` within session (and ideally by `history_tokens` if cheaply available).
   - For a mutated call at `idx=K`, the counterfactual is the stable-cohort mean at `idx=K` for the same model/provider — not the global mean. Naive global differencing attributes turn-13 cache savings to turn-2 mutations and overstates the loss.
   - Better still: fit a small regression on the stable cohort (`cache_read ~ idx + log(history) + model`) and report the residual on mutated calls. Same machinery analyze.py already uses for cohort math.
2. **Drop the `floor at 0`.** It's a one-sided estimator — guaranteed to never report a gain even when a mutation happens to coincide with a legitimate cache refresh. Either report signed differences or rename the field `cache_read_tokens_lost_upper_bound` and own that it's a worst-case bound.
3. New summary field `estimated_net_savings_tokens_cache_adjusted` = `tokens_saved` − `cache_read_tokens_lost × miss_premium`.
4. Per-provider price table (Anthropic Sonnet, gpt-5.4, etc.) for the miss_premium factor. Single source of truth, used by both the savings ledger and the auto-detect threshold reasoning.
5. Update `summary_payload`, `format_summary`, `markdown_report`. The old number stays as `_legacy_tokens_saved` for back-compat in change logs.

Exit criteria: the analyzer's headline number reflects net reality on this 219-call sample, with matched-counterfactual methodology documented.

### Phase 6 — doc + marketing-copy cleanup

1. Update [STRATEGY.md](02.strategy-2026-05-12.md), [PLAN.md](03.plan-2026-05-12.md): describe the cache-on default; mark per-turn narrowing as the `cache_off` fallback.
2. Update [website-copy](13.website-copy-feature-bank-2026-05-19.md), [product-page](14.website-copy-product-page-2026-05-19.md): the "57% / 3.37M" headlines need restatement once Phase 5 lands. Phrasing pivots from "narrows tools per message" to "shapes tools per session, recovers on demand."
3. Move the harvest follow-ups doc into the `resolved/` pattern or rescope — Phase 2 makes the manual broaden-trigger work redundant for cache-on profiles.

## What dies in this refactor

| Component | Cache-on behavior |
|---|---|
| Per-turn `predictor.predict()` inside `pre_gateway_dispatch` | Skipped after session-start freeze |
| Sticky residency (`_STICKY_BY_KEY` and friends) | Skipped — frozen set already carries forward |
| Lookback ring (`_PRIOR_MESSAGES_BY_SESSION`) | Skipped — predictor isn't running per turn |
| `_decay_sticky`, `_live_sticky`, `_refresh_sticky` | Dead code paths in cache-on mode |
| `bypass_rate` A/B cohort | Reframed: bypass now applies to the freeze decision, not per-turn |

All of these stay alive for cache-off mode (kimi, gpt-5.4-mini, anything provider-side caching doesn't reach).

---

## What stays exactly as-is

- `expand_tools` — the safety valve. Model asks; plugin grants; one cache break paid. Identical mechanics.
- `_wrap_build_api_kwargs` filter logic — still narrows kwargs to `allowed_set`, just sources `allowed_set` from a frozen decision instead of a per-turn one.
- Telemetry shape (predictions.jsonl, tool_calls.jsonl, api_calls.jsonl). New fields, no removed fields.
- `analyze.py` cohort comparison machinery — gains a cache-mode dimension.

## Open questions (defer until they bite)

1. **Freeze granularity for subagents.** Phase 1 nominates "subagents always run unnarrowed" as the default. Revisit if delegation-heavy workflows show meaningful waste.
2. **Between-session shaper key.** `scope` (agent:platform) alone, or `scope + working_dir hash` for CLI sessions? Punt to Phase 2 design.
3. **Mnemosyne deeper integration.** If the pre-Phase-1 Mnemosyne A/B shows injection IS materially busting cache, this becomes a much bigger conversation — either coordinate with Mnemosyne to make injection prefix-stable, or accept that dynamic-tools' freeze is a partial win.

## Sequencing

Build Phase 0 → 1 → 3 → 4 → 2 → 5 → 6. Reasoning:

- Phase 1 alone gives the headline win and is testable on Bernard's existing telemetry shape.
- Phase 3 (auto-detect) before Phase 2 (between-session shaper) because auto-detect protects users from misfiring the freeze on cache-off providers — that's a correctness gate, not an optimization.
- Phase 4 before Phase 2 so compaction-driven re-freezes are part of the production path the shaper observes.
- **Phase 2 before Phase 5** so the savings ledger measures the steady-state freeze (post-shaper), not the cold-start freeze. Reporting a number now and again after Phase 2 means restating the headline twice — wasted credibility.
- Phase 6 always last.

The prior draft had Phase 2 after Phase 5; that was calendar reasoning ("Phase 2 is the biggest lift") leaking into architecture. Corrected.
