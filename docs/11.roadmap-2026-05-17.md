## Queued

### 1. `apply.py` — the auto-apply writer

The missing capstone of the adaptive layer. Design lives in
[AUTO-APPLY-PLAN.md](04.auto-apply-plan-2026-05-12.md). Mechanical prereqs (items
#1, #2, #5 of the telemetry audit) cleared 2026-05-17; harvest data
provides robust signal so the build can start without waiting for the
behavioral prereqs (#3, #4 — pending post-restart organic data).

The shape (per AUTO-APPLY-PLAN):
- Reads `learned_recommendations.json` (analyzer output) + harvest
  recommendations
- Filters under strict gates (precision ≥ 0.95, support ≥ 5, max 3
  dampener applies per run, max 5 total changes per run)
- Writes `learned.json` + an append-only change log
- Idempotent — re-running with no new telemetry produces zero changes
- Auto-demote path: revert promotions whose post-promotion telemetry
  shows zero use over 50+ turns

**Blocked on:** the install → configure → apply flow questions below.
Don't start until those are answered — they shape what apply.py writes
to vs what stays manual.

### 2. Auto-bootstrap on plugin first activation

Today [scripts/bootstrap.py](scripts/bootstrap.py) must be invoked
manually. Wiring it into `register()` would close the
"install, activate, done" loop literally: plugin detects empty live
telemetry + non-empty `sessions/` and runs harvest in background, then
surfaces TOP ACTIONS on the next user message.

Open implementation questions:
- Sync vs async? Can't block `register()` for seconds. Likely:
  background thread, plugin signals when ready.
- How to surface notifications to the user through Hermes? (Slack DM?
  Telegram message? Just a log line?)
- What if the user has zero sessions? (cold-start fallback — keep
  current behavior, no warm-start magic possible)

### 3. Public-release prep

For STRATEGY.md's "Official Hermes-plugin readiness" gate:
- README rewrite as user-facing first, not dev-facing first (mostly
  done in the 2026.5.17-beta migration; needs a final pass with fresh
  eyes once the install → configure → apply flow is settled)
- Standalone-repo install path verification — actually run
  `hermes plugins install dalemugford/hermes-dynamic-tools` on a clean
  Hermes install and confirm it works end-to-end
- Drop the `-beta` suffix from the version when external install
  confirms it works
- Announcement / release notes for the first non-beta cut

## Open design questions (talk through before building #1)

These shape what `apply.py` actually does. Worth aligning before any
code lands.

### Q1: Is `learned.json` the single canonical write target for apply.py?

AUTO-APPLY-PLAN currently says yes — apply.py only writes
`learned.json`, never edits `policy.yaml` or `config.yaml`. Confirm:
does this hold for all change types (promotions, demotions, learned
dampeners)? Or do some live more naturally in `policy.yaml` (e.g.,
trigger-keyword broadenings that emerged from
`--suggest-trigger-keywords`)?

**Tradeoff:** `learned.json` is gated by `learned_mode`, so it's
revert-safe. `policy.yaml` is user-curated and auto-editing it crosses
a different trust line. But trigger-keyword changes are global to a
scope and naturally feel more "policy" than "learned overlay."

### Q2: What's THE recommended path for a new user?

Today there are four ways to change behavior:
1. Edit `policy.yaml` (the global default for everyone using the
   shipped plugin)
2. Edit `config.yaml`'s `always_on_extra` / `always_off` (user-scoped,
   easy to read in the user's main config)
3. Edit `learned.json` by hand (machine-format, requires understanding
   the schema)
4. Let `apply.py` write `learned.json` automatically (the
   "magically, quietly" path)

`bootstrap.py` today recommends path #2 (manual edit of config.yaml).
That's the safest. But the "install, activate, done" promise points at
path #4. Decision: which is the **documented default** in the README?
Are paths #2 and #4 both first-class, or is one the recommendation and
the other a power-user option?

### Q3: Do per-scope `always_on_extra` edits in `config.yaml` belong in apply.py's scope?

Today `learned.json` per-scope `always_on` is functionally equivalent
to `config.yaml`'s `channels.<scope>.always_on_extra`. So apply.py
*could* write either. But:

- `config.yaml` is the user's main config — auto-editing it might
  surprise users who edit it frequently for unrelated reasons.
- `learned.json` is in a state-dir, off the user's radar, and
  visibly machine-written.

Current lean (from AUTO-APPLY-PLAN): apply.py only touches
`learned.json`. Confirm.

### Q4: How does a user revert an applied change?

Three options:
- **Toggle `learned_mode: off`** — disables ALL learned-overlay
  application at once. Heavy hammer; loses all auto-applied wins.
- **Edit `learned.json` by hand** — surgical but requires knowing the
  schema and trusting future apply.py runs not to re-add the entry.
- **`apply.py --revert <change-id>`** — explicit, surgical, logged
  in the change log. Most ergonomic but most code.

Whichever we pick shapes how apply.py handles re-runs: if a user
manually removes an entry from `learned.json`, does the next apply.py
run treat the removal as "ignore" or "candidate for re-apply"?
