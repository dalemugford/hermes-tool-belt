## Guiding Principle

**Actuators before analyzer.** Build the levers that manipulate tool policy first. Then build the analyzer that reads telemetry and moves those levers. This enables validation: the analyzer makes a prediction, the actuator applies it, and telemetry confirms whether the prediction was correct.

## Current State (What's Working)

**Mechanism:**
- Plugin patches `AIAgent._build_api_kwargs` to narrow tools per API call
- Predictor uses regex triggers + attachment detection + `exclude_keywords` dampeners
- `expand_tools` meta-tool recovers cut tools on-demand with sticky TTL (default 3 turns)
- Sticky residency is per-session (opaque sha1 key), not per-scope — no cross-session leakage
- Telemetry writes `predictions.jsonl` and `tool_calls.jsonl` with full tool-name sets
- Tool-call telemetry correctly attributes expansion-driven use (post-2026-05-17 fix; rows with `was_initially_available: true` are not credited)
- Trigger FP classification uses session-bounded N-turn (N=3) lookahead, falling back to same-prediction when session_id is blank

**Measurement / validation:**
- **Savings measured (pre-audit archive):** 3.37M tokens saved across 109 sessions, 57% reduction vs baseline. Token-savings math wasn't affected by the audited bugs.
- **Per-tool cost measured:** ~388 tokens per tool per API call
- **Smoke test** ([scripts/smoke-test.py](scripts/smoke-test.py)): 109 synthetic scenarios in <1s validate session_id population, bypass cohort, expand attribution, cross-session isolation, on_session_end eviction. Run after any gateway restart.
- **Privacy invariants** (harvest output): tool args never written; message text never appears in derived files beyond 80-char preview. Enforced by tests/test_harvest_privacy.py.

**Harvest infrastructure:**
- [`scripts/harvest-replay.py`](scripts/harvest-replay.py): reads `sessions/*.jsonl` per profile, runs predictor against historical toolsets, emits synthetic `predictions.jsonl` + `tool_calls.jsonl` tagged `source: harvest` to a separate `state/dynamic-tools/harvest/` subdir.
- [`scripts/bootstrap.py`](scripts/bootstrap.py): wraps harvest + analyzer into a single first-install UX with ranked TOP ACTIONS summary.
- Analyzer harvest-aware mode: per-tool `harvest_tool_promotion` recommendations (was_cut × round-trip vs predictions × per-tool carry math), plus `--suggest-trigger-keywords` mining of cut-tool message previews.

**Tests:** 43 unit tests + 8 smoke-test assertions, all green.

## What's Built / What's Missing

The plugin now manipulates tools through:
1. **Static policy YAML** ([`policy.yaml`](policy.yaml)) — hand-curated always_on + trigger groups
2. **Manual config overrides** (`always_on_extra`, `always_off`) in `config.yaml` per scope
3. **Temporary sticky** (`_STICKY_BY_KEY`, session-scoped, in-memory only, TTL-based)
4. **Learned state** ([`learned.py`](learned.py) consuming `~/.hermes/state/dynamic-tools/learned.json`) — persistent per-scope overlays, applied only when `learned_mode` permits
5. **Analyzer recommendations** ([`analyze.py`](analyze.py)) — deterministic telemetry pass that emits markdown reports and `learned_recommendations.json` covering: expanded_category recs, harvest_tool_promotion recs, trigger_quality recs, dampener_candidates, trigger_keyword_candidates

**Still missing — the actual auto-apply writer:**
- `apply.py` (per [AUTO-APPLY-PLAN.md](04.auto-apply-plan-2026-05-12.md)): the writer that consumes `learned_recommendations.json` under strict gates and updates `learned.json` with rate-limited changes + audit trail. Mechanical prereqs are cleared, so v1 can start now; live Bernard cohort comparison still waits on post-restart accumulation.
- Auto-bootstrap on plugin first activation: today `scripts/bootstrap.py` must be invoked manually. Wiring it into `register()` would close the "install, activate, done" loop literally.

## Phase 1: Actuators (The Levers)

**Goal:** Give the plugin persistent, programmatic control over tool policy per scope.

### 1.1 Learned State File ✅

**Path:** `~/.hermes/state/dynamic-tools/learned.json`

**Schema:**
```json
{
  "version": 1,
  "updated_at": "2026-05-08T17:45:00Z",
  "scopes": {
    "bernard:telegram": {
      "always_on": ["terminal"],
      "always_off": [],
      "trigger_adjustments": {
        "shell": {"action": "demote", "reason": "78% false positive rate", "since": "2026-05-08"}
      },
      "promotions": {
        "terminal": {
          "promoted_at": "2026-05-08T17:45:00Z",
          "triggered_by": "analyzer",
          "usage_before": 0.19,
          "usage_after": null,
          "sessions_measured": 0,
          "est_cost_per_session": 1670
        }
      }
    }
  },
  "global": {
    "always_off": ["homeassistant"]
  }
}
```

**Key fields:**
- `scopes.<scope>.always_on` — tools permanently added to always-on for this scope
- `scopes.<scope>.always_off` — tools permanently removed for this scope
- `scopes.<scope>.trigger_adjustments` — per-trigger tuning (boost, demote, disable)
- `scopes.<scope>.promotions` — audit trail for each promotion (when, why, cost, measured effect)
- `global` — scope-agnostic overrides

**Design notes:**
- Human-readable JSON, not a database. Easy to inspect, edit, version-control.
- Schema versioned for migrations.
- Promotions carry measurement metadata so the analyzer can evaluate its own predictions.
- File is read-only during prediction, written only by analyzer or explicit user action.

### 1.2 Merge Learned State into Preset Resolution ✅

**File to modify:** `presets.py` (`_resolve_preset_inner`)

**Change:** After applying channel overrides, load `learned.json` and merge:
1. Add `learned.always_on` tools to the always_on list
2. Remove `learned.always_off` tools from always_on and from trigger tools
3. Apply trigger adjustments:
   - `boost` → lower threshold (currently no threshold, so this may be a no-op; placeholder for future scoring)
   - `demote` → remove trigger entirely for this scope
   - `disable` → same as demote

**File to modify:** `__init__.py` (`_load_user_config` or new `_load_learned_state`)

Add a loader that reads `learned.json` into `_LEARNED_STATE` global, refreshed when the file mtime changes (not on every prediction).

### 1.3 Config Mode: learned_mode ✅

**Add to config schema:** `plugins.dynamic-tools.learned_mode`

**Values:**
- `off` — ignore learned.json entirely (default for safety)
- `recommend` — analyzer writes recommendations to a separate file (`learned_recommendations.json`); plugin does not apply them
- `auto` — plugin applies learned state written by an external analyzer/apply step; direct analyzer writes remain future work
- `audit` — apply learned state (same merge as `auto`); the `learned_mode` field stamped into each prediction row identifies audit runs so they can be grepped or analyzed separately from `auto` runs. No additional per-decision flag is emitted today; if a finer-grained audit signal is needed later, add it to `_maybe_log_prediction` rather than splitting the merge path

**Rationale:** Users should be able to try the adaptive layer without giving up control. Start with `recommend`, graduate to `audit` or `auto` once validated. The shipped default remains `off`.

### 1.4 Expand Tools → Learned State Bridge ✅

**Files modified:** `__init__.py` (`_refresh_sticky`, `_on_post_tool_call`, helper functions)

When `expand_tools` is called and a tool from the expanded category is actually used within the current or sticky window, the plugin now logs an "expand used" signal. This is a strong promotion input for the analyzer because it distinguishes speculative expansion from expansion that led to real tool use.

**Schema addition to `tool_calls.jsonl` on the actual expanded tool call:**
```json
{
  "expand_tools_used": true,
  "expanded_tool": "terminal",
  "expand_category": "terminal",
  "turns_until_used": 2,
  "expansion_prediction_id": "..."
}
```

**Notes:**
- Existing prediction rows are append-only and are written before the expanded tool is used, so the actual use signal lives on the corresponding tool-call row rather than rewriting `predictions.jsonl`.
- Unrelated calls after `expand_tools` are marked with `expand_tools_used: false` and do not consume the pending expansion. A later real call to the expanded tool still records the positive signal.
- Sticky-window use is linked through in-memory sticky metadata: category, source prediction id, and turn counter.

## Phase 2: Analyzer

**Goal:** Read telemetry, calculate per-scope patterns, write recommendations or direct changes to learned state.

**Precondition:** Phase 1 actuators are in place and at least `learned_mode: recommend` is supported.

### 2.1 Analyzer Script: `analyze.py` ✅

**Location:** `~/.hermes/plugins/dynamic-tools/analyze.py`

**Implemented:** Deterministic first-pass analyzer that reads append-only telemetry, tolerates old rows with missing fields, prints a stdout summary, writes markdown reports under `reports/`, and can optionally emit `learned_recommendations.json` in recommendation format. It does not write `learned.json`; auto-apply remains future work so default behavior stays safe/off.

**Hardening added after the first pass:**
- `--format json` for machine-readable stdout. File path notices are sent to stderr in JSON mode so stdout remains parseable.
- `--include-archives` opt-in support for matching JSONL files under `state-dir/archive/`; live/current files remain the default input set.
- Recommendation payloads now include `status`, `metrics`, `defaults`, and a `proposed_learned_patch` shape for future human review/apply work.
- One-off expansions below the default minimum expansion floor are explicitly marked `status: insufficient_data` and stay watch-only.
- Reports include same-scope trigger precision/recall proxies from `trigger_tools_by_group` and actual tool calls when those fields exist.
- Always-on unused analysis now reports estimated carrying cost using `--per-tool-tokens` as an adjustable lever.

**Inputs:**
- `predictions.jsonl`
- `tool_calls.jsonl`
- `learned.json` remains optional/future context; current analyzer does not require it

**Outputs:**
- stdout summary
- markdown report under `reports/` by default
- optional `learned_recommendations.json` with `--write-recommendations`

**Current metrics:**
- per-scope prediction/session counts and expansion counts
- event-level expansion success from unique expansion events with downstream use, plus row-volume follow-through from `expand_tools_used: true` rows
- `turns_until_used` average/median/sample count
- promotion/watch candidates by scope/category, with explicit insufficient-data handling
- always-on unused candidates when carried for enough turns with no logged calls, including carrying-cost estimates
- same-scope trigger precision/recall proxies when `trigger_tools_by_group` is available

**Thresholds:** All thresholds are command-line defaults/levers (`--min-expansions`, `--promote-expand-rate`, `--promote-use-rate`, `--unused-carry-turns`, `--per-tool-tokens`, `--trigger-min-fires`). They should be tuned from measured re-invocation rates and latency rather than treated as permanent truth.

### 2.2 Core Metrics (Deterministic) ✅ / partial

The analyzer does not need an LLM. Implemented metrics are aggregation queries and deliberately conservative with old telemetry rows.

**Per tool/category, per scope:**
- `expand_rate` — expansion events as a share of prediction turns for the scope
- `usage_after_expand` — unique expansion events with downstream use divided by expansion events; `expanded_tool_use_rows` remains a separate row-volume metric
- `carrying_cost` — estimated always-on token cost using `--per-tool-tokens`
- `net_recommendation` — promote_candidate / watch_high_precision / watch / keep_gated / demote_candidate

Still planned:
- true per-session `sessions_without_tool`
- richer `expand_penalty` that accounts for extra model-call latency and turn burn
- before/after measurement once learned state is applied in real sessions

**Per trigger, per scope:**
- `fire_rate` — % of sessions where trigger fired
- `precision` — % of fired sessions where trigger tools were used
- `recall` — % of sessions needing trigger tools where trigger fired
- `recommendation` — tighten / loosen / demote / no-change

### 2.3 Promotion Thresholds ✅ / first default levers

Based on the measured per-tool cost (388 tokens/API call), analyzer v1 uses adjustable defaults rather than fixed policy truth:

```
if expand_rate > 0.50 and usage_after_expand > 0.80:
    recommend PROMOTE (tool is needed in most sessions)
elif expand_rate < 0.10 and usage_after_expand < 0.50:
    recommend DEMOTE (tool is rarely needed; if trigger-fired, it's probably a false positive)
elif sessions_without_tool > 0.90:
    recommend ALWAYS_OFF (tool is dead weight for this scope)
```

**Example from current data:**
- Terminal: expanded in ~19% of sessions, used in 100% of expanded sessions. Borderline for promotion. Carrying cost: ~1,670 tokens/session. For `bernard:telegram`, this might be worth it.
- Browser: expanded rarely, used rarely. Likely demote or keep trigger-only.
- Home assistant: never expanded, never used. Candidate for `always_off`.

### 2.4 Validation Loop ⏳ next

The analyzer is not a one-shot. It measures its own predictions after a recommendation is deliberately applied:

```
Week 1: Analyzer recommends "promote terminal for bernard:telegram"
Week 2: Plugin applies learned state
Week 3: Analyzer checks: "terminal expanded in 0% of sessions (it was always on), 
         terminal used in 95% of sessions (good), carrying cost: 1,670 tokens/session"
         → recommendation CONFIRMED
```

If a promoted tool is unused for N sessions, the analyzer can recommend demotion.

### 3.2 Trigger Dampeners and Suppressed-Trigger Telemetry ✅ implemented / live-verified

Plan saved in `TRIGGER-SCORING-PLAN.md`. The file name is historical; the current direction deliberately defers the full scored-trigger framework. The implemented slice keeps binary regex triggers and adds a lighter negative-veto layer (`exclude_keywords`) for `file_write`, `delegation`, and `cronjob`, plus suppressed-trigger telemetry.

Implementation details now live in the plugin:
- `presets.py` parses `exclude_keywords` into `TriggerGroup.exclude_patterns`.
- `TriggerGroup.matches()` checks exclude patterns before positive keyword/attachment matching.
- `predictor.py` records `triggers_suppressed` when a positive signal would have matched but an exclude vetoed the trigger.
- `logger_io.py` writes `triggers_suppressed` into `predictions.jsonl`.
- `policy.yaml` contains the current dampeners for `file_write`, `delegation`, and `cronjob`.
- `scripts/check_trigger_dampeners.py` is the smoke fixture for dampener behavior.

Live verification after the 2026-05-11 gateway restart showed the dampener path active: Dale's Telegram check message fired `shell` but recorded `triggers_suppressed: ["file_write"]` because the phrase “Don’t change settings…” vetoed the otherwise-positive file-write signal.

Current recommendation:
- Do **not** promote `terminal` to always-on yet; analyzer output still says keep it gated, and Telegram has enough conversational turns that the carrying cost deserves a tighter calculation.
- Do **not** build score thresholds, weighted signals, or a trigger-lab analyzer yet.
- Keep the dampeners small and explicit. Do not add the full scored-trigger framework unless live telemetry shows remaining false positives/false negatives that simple vetoes cannot handle.

### 3.3 Revert Mechanism ⏳ planned

Every promotion in `learned.json` carries a measurement window. If `usage_after_promotion` drops below threshold for N consecutive sessions, the analyzer flags it for demotion. The user (or auto-mode) removes it from `always_on`.

### 3.3 Human Override ⏳ planned

Users can always edit `learned.json` directly. The analyzer never overrides manual entries unless explicitly cleared. Add a `manual: true` flag to hand-edited entries.

## 2026-05-12 Measurement-Layer Additions

Four changes shipped together to make the analyzer's recommendations more
honest and to give the policy layer finer-grained scope for learning.

### 1. Expand-tools round-trip cost accounting ✅

`analyze.py` now subtracts the estimated cost of each `expand_tools`
round-trip from headline savings and folds it into per-category
recommendation math.

- New default `DEFAULT_EXPAND_ROUND_TRIP_TOKENS = 1500` (CLI override:
  `--expand-round-trip-tokens`). Tune to a measured baseline once we have one.
- Per-category recommendation rows now report `saved_round_trip_tokens`,
  `added_carry_tokens`, `net_value_tokens`, and `tools_in_category` (derived
  from `expand_event.resolved_tools` in tool_calls.jsonl).
- New action `review_net_negative` flags categories that pass the
  expand-rate/use-rate thresholds but have negative net token value under
  the current defaults.
- `summary_payload` and `scope_payload` carry
  `estimated_expand_round_trip_cost_tokens` and `estimated_net_savings_tokens`.

This addresses the gap noted in §2.2: *richer `expand_penalty` that accounts
for extra model-call latency and turn burn*. Latency is still unmodeled;
token cost is.

### 2. Predictor lookback ✅

Conversational replies like “yes” / “go ahead” / “no, don't” carry zero
signal on their own. The predictor now optionally prepends recent
same-session user messages before regex classification.

- New config: `plugins.dynamic-tools.predictor.lookback_turns` (default `1`,
  `0` disables).
- In-memory `_PRIOR_MESSAGES_BY_SESSION` ring keyed by `session_id`. Cleared
  on `on_session_end`; bounded to `lookback_turns + 1` entries per session.
- Composed predictor input tags prior turns with `[prior]:` so dampener
  regexes still anchor cleanly and the marker itself doesn't introduce false
  positives.
- Telemetry: predictions.jsonl gains `lookback_used` (count of prior
  messages actually concatenated this turn) and `lookback_turns_config`.
- Dampeners interact correctly: when the prior turn was conversational
  (“should we update the README later?”), the existing `exclude_keywords`
  veto still suppresses the trigger and stamps `triggers_suppressed`.

### 3. A/B baseline bypass cohort ✅

Headline savings (“57% reduction”) are tautological without a control —
we need to know whether narrowing degrades behavior. The plugin now
deterministically bypasses a configurable fraction of sessions.

- New config: `plugins.dynamic-tools.bypass_rate` (default `0.0`), with
  per-scope overrides via `channels.<scope>.bypass_rate`.
- Decision is deterministic via SHA-1(`scope|session_id`) so a session is
  consistently in or out of the bypass cohort across all its turns.
- Bypassed turns still run the predictor (telemetry stays useful) but
  override `allowed_tool_names` to `WILDCARD_ALWAYS_ON` and stamp
  `policy_source: "bypass"` in the prediction row.
- Analyzer cohort comparison ✅: per-scope `cohorts.<policy_source>` payload
  reports `predictions`, `sessions`, `tool_calls`, `tool_calls_per_prediction`,
  `expand_tools_events`, and `expand_rate`. First slice is rollup-only; per-
  session deltas (turn count, latency) are future work.

### 4. ~~Scope is now agent:platform:kind~~ — **reverted**

### 5. Auto-suggest dampener candidates from telemetry ✅

The analyzer can now mine candidate `exclude_keywords` patterns by
examining message previews where a trigger fired but no matching tool
got called.

- New CLI flag `--suggest-dampeners` (off by default).
- Per-(scope, trigger) collection of FP and TP message previews
  (`trigger_fp_previews`, `trigger_tp_previews` on `ScopeStats`), capped
  at 500 entries each to bound memory.
- N-gram extraction (2–4 words, configurable) with FP-share precision
  filter (default ≥0.8) and minimum support (default ≥3 occurrences).
- Substring-dominance dedupe: longer, more specific n-grams win when they
  retain ≥80% of a shorter form's support; otherwise the shorter, more
  general form wins.
- Existing-dampener overlap filter: loads the preset's `exclude_keywords`,
  compiles to regex, drops any candidate already vetoed by an existing
  pattern. Smoke test confirms `should we` is filtered out because the
  current aggressive preset already vetoes it.
- Output: ranked candidates per (scope, trigger) with `fp_count`,
  `tp_count`, `precision`, `suggested_regex`, and up to 3 sample previews
  for human sanity-check. Appears in stdout JSON, markdown report
  ("Suggested Dampener Candidates" section), and the recommendations
  JSON when `--write-recommendations` is set.

This closes the loop in §2.2's per-trigger metrics:
**telemetry → false-positive mining → human-reviewed candidate → tighter
YAML → fewer false positives next batch**, without growing the trigger
DSL into a full scoring framework.

### 6. Simplification pass ✅

Two reductions landed back-to-back as a single shed:

**6a. Single shipped policy.** Three named presets
(`aggressive` / `balanced` / `conservative`) collapsed into one
`policy.yaml` at the plugin root. The `mode` config key is gone. The
kill-switch use case (formerly `mode: conservative`) is now
`bypass_rate: 1.0` per scope — the same mechanism the A/B cohort
already uses. Rationale: we only ever tested with `aggressive`; three
presets implied "pick one" while the calibration flow wants "one
warm-start seed that gets adapted"; `bypass_rate` already covered the
kill-switch case.

**6b. Reverted `agent:platform:kind` to `agent:platform`** (was §4
above). The three-level hierarchy added cost in three lookup sites plus
a derivation helper plus a telemetry field, with no evidence yet that
the DM/group/thread/cron split changes policy in a useful way. Re-add
when a profile proves it matters.

Affected files (combined):
- `presets/aggressive.yaml` → `policy.yaml` (moved to plugin root)
- `presets/balanced.yaml`, `presets/conservative.yaml` — deleted
- `presets.py` — `load_named_preset()` → `load_base_policy()`;
  `_channel_config()` back to two-level fallback
- `__init__.py` — `mode` config key dropped; `_agent_platform_from_context`
  back to 3-tuple; `_derive_kind` / `_normalize_kind` / `_KIND_ALLOWED`
  removed; `_bypass_rate_for_scope` back to two-level
- `learned.py` — `scope_candidates()` back to two-level
- `analyze.py` — `_load_preset_excludes()` no longer name-dispatches;
  `--dampener-preset` CLI flag removed; `normalize_scope` drops `kind`
- `logger_io.py` — `PredictionRecord.kind` removed
- `scripts/check_trigger_dampeners.py` — points at `policy.yaml`
- `config.yaml` (Bernard) — `mode: aggressive` removed; scope key
  changed from `bernard:telegram:dm` to `bernard:telegram`
- README / STRATEGY / CALIBRATION / AUTO-APPLY docs updated

No backward-compat path — Dale is the only user. `mode:` and `kind`
fields in old telemetry rows are simply ignored.
